# A04 Next Step: one-cell MBIR stack loop

This is the current execution plan for A04. It supersedes the older duplicated
loader-first plan. The scope is deliberately below a complete MBIR VM.

## Current verified ground

- `src/byte_dispatch18.hell` classifies all 18 opcode bytes, but handlers are
  markers rather than MBIR operations.
- `src/byte_push_const_out.hell` consumes `01 <operand>` and emits the operand
  in the same handler. It does not store a stack value or fetch another
  opcode.
- `src/cell_stack_top.hell` stores and recovers one byte in a dedicated cell,
  but is a one-shot echo probe, not connected to opcode dispatch.
- `src/byte_push_const_cell_probe.hell` consumes a known `01` prefix, then
  stores and recovers the operand through the existing two-level cell route.
  `evidence/push_const_cell_operand_smoke.json` records 4/4 matches on the
  Python oracle and a local source-built Classic engine. The prefix is not
  classified; output is only a probe observation, not a separate `OUT_BYTE`.
- `src/byte_push_const_dispatch_cell_probe.hell` now classifies `01`, reads the
  operand, stores/recovers it through the dedicated cells, and emits it. Its
  6/6 oracle/runner cases are in
  `evidence/push_const_dispatch_cell_smoke.json`.
- `src/byte_push_const_later_fetch_probe.hell` additionally consumes one later
  byte before recovering/emitting the stored operand. Its 6/6 probe cases are
  in `evidence/push_const_later_fetch_smoke.json`. The control `01 41 00`
  emits `41`, confirming that the later byte is not dispatched yet.
- `evidence/cell_two_read_negative.json` records a failed second-input
  experiment. `evidence/byte_twofetch_negative.json` records a failed
  `01 <operand> 10` experiment. Neither establishes that repeated fetch works.

See `A04_STATUS.md` for the full evidence ledger. A source file or successful
assembly alone is not a positive result.

## Next milestone

Make one Malbolge program handle this MBIR byte stream as data:

```text
01 41 10 00
```

Expected behavior: `PUSH_CONST 0x41` stores `0x41` in a dedicated stack cell;
the next fetch dispatches `OUT_BYTE`, which recovers and emits `0x41`; the
following fetch dispatches `HALT`.

The program must use one unchanged `.mb` runtime for all test streams. Input
bytes may vary; generated code must not contain the expected operand/output.

## Implementation sequence

1. DONE (partial): integrate the operand cell route with the opcode classifier
   so `01` is validated and its operand is stored by the `PUSH_CONST` handler.
2. PARTIAL: the operand now survives one later `IN`; implement `OUT_BYTE` as a
   separately dispatched handler that recovers the stored byte. The current
   output still follows the `PUSH_CONST` path.
3. Add a fetch loop that requests one opcode per iteration. Reset every
   self-modifying value and return cell that the next iteration depends on.
4. DONE for these probes: dedicated generators produce both source variants
   reproducibly from checked-in inputs.
5. PARTIAL: positive and negative evidence exists for the bounded cell and
   later-input claims. The full acceptance gate remains unpassed; don't promote
   the VM-level status until the later opcode and trailing HALT are dispatched.

Integration finding: the dispatch path self-encrypts its shared `MOVED`
instruction. The `PUSH_CONST` handler must issue `R_MOVED` immediately after
the operand `IN`; without it the composed probe emitted constant `54` for
every operand. With the restore, the classifier + dedicated-cell probe passes
for `41`, `7a`, and `00` on both engines.

For the later-fetch probe, preserve the landing's first `R_MOVED`, then run the
extra `IN`, then run a second `R_MOVED` before cell recovery. Putting the extra
`IN` before the landing restore produced `a8`; this ordering passes both
engines.

The stored byte also survives one subsequent `IN` when the landing begins with
the original `R_MOVED`, consumes the byte, then restores `MOVED` again before
cell recovery. The probe passes operands `41`, `42`, `7a`, and `00` after a
later byte of `10`; `01 41 00` still emits `41`, so this is persistence across a
fetch only, not `OUT_BYTE` dispatch.

On the exact gate streams `01 41 10 00` and `01 42 10 00`, outputs happen to
match and halt, but both take the same 52,187 steps as the three-byte input:
the final `00` is ignored. The control `01 41 00` emits `41` instead of halting
empty. This is a direct gate failure, not just a missing generality claim.

Space check: the base composite assembles to 48,400 bytes; the later-fetch
variant is 48,676 bytes in the 59,049-cell Classic memory, leaving 10,373
cells. A standalone contiguous classifier through opcode `10` is 45,950 bytes,
so it cannot simply be appended as a second dispatch stage. The next
integration needs to reuse/compact the first classifier's helpers and reset
its mutated state, or build a smaller equality/return path for `10`. The
existing zero/nonzero classifier (`src/byte_dispatch1.hell`) is 25,383 bytes
compiled standalone: closer, but still too large to append unchanged. The
acceptance vectors only require distinguishing `00` from `10`, so sharing its
digital-root/decrement helpers is the most promising next experiment.

Reference check against `/home/danny/Development/clasesbolge.md`: its inverse
formula `(opcode - c) mod 94` encodes a desired instruction at load time. It
does not classify an input byte at runtime. Runtime dispatch still depends on
`(mem[c] + c) mod 94`, while executed source cells are encrypted; therefore
the static codec cannot replace the missing second-stage state/dispatch logic.

## Acceptance gate

- `01 41 10 00` emits exactly byte `41` and halts.
- `01 42 10 00` emits exactly byte `42` with the same runtime artifact/hash.
- `00` halts without output.
- `01 41 00` halts without output (stored value is unused).
- Oracle and real runner agree on output and halt behavior for every case.
- Evidence records runtime/source hashes, assembled artifact hash, input bytes,
  expected and observed output, runner identity, steps, status, and verdict.

`vm_malbolge/tests/buildrun.py` now uses normal layout by default; `-f` is
available only through the explicit `--fast-layout` option. Fast layout has
produced runner-specific false failures for some dispatch programs, so a
fast-layout-only result is not acceptance evidence.

## Deferred until this gate passes

- multi-byte stdin loader and bounded program storage;
- arithmetic, branches, locals, calls, and the remaining MBIR opcodes;
- MBIR-to-HeLL lowering for arbitrary programs;
- source-language frontend integration.

`mbir_vm.hell` remains a design stub until this milestone has evidence.
