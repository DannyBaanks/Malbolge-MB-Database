## Root cause (isolated, one line from fixed) — **[HISTORICAL: superseded by findings 14-20]**

The decrement tail's `SUBROUTINE_FLAG6` line is pointed at `lt_false` (a leftover
from an earlier revision). The b-class `dec#2` is armed with `SUBROUTINE_FLAG6`,
so its return lands on that line and pushes the boolean immediately, skipping
the pass-2 transition entirely. Traced and confirmed: after `lt_dec2`'s
`dec#2`, the tail's SUB6 line fires and control reaches `lt_false` at step
~70,952 without any `reset_and_loop` between. The a-class `dec#2` (also armed
SUB6 by the shared `lt_dec2`) returns to the same place, which is why every
`b>=1` vector skips pass 2.

**Why the obvious fix does not land:** repointing that line to `lt_dec2_ret`
(the shared dispatcher that already separates pass 1 from pass 2 via
`PUSH_FLAG4`) is semantically correct, but it changes an ADDRESS VALUE in the
compiled image. LMAO's init-code generation is value-dependent (the
data-module crazy chain for a constant has a value-dependent length), so the
init code grows, the whole program re-lays-out, and the xlat2 cycle of the
`SLOT1_FLAG` trampoline that the post-push OUT depends on shifts: the OUT then
pops the cleared Slot 1 instead of Slot 0 and prints `a8` in an EOF loop.
Confirmed experimentally (v19): the repoint breaks all 9 vectors, including
`(0,0)` which was passing.

## Established facts for the next attempt

1. **Single-pass is impossible**: exhaustive search over read orders x op
   sequences (crz with C0/C1/C2/C20/C21, dec) x 3-dec signatures found zero
   programs separating `a<b`, because `(0,0)` and `(0,1)` are
   informationally identical after the standard pop idiom (both give
   value=0, value_C1=29524).
2. **The two-pass design with a marker is necessary and works** up to the
   routing bug above.
3. **The marker must be a virgin gate.** `SLOT1_FLAG` is consumed by the
   post-push OUT path; extra executions on it (dummy clears, arms, checks)
   shift its xlat2 cycle and the OUT starts popping Slot 1. The dedicated
   `LT_B1` flag (added at 2 cells) fixes this and is what the current
   revision uses.
4. **The `OP1_FLAG` line at the head of `return_from_dec_op2_1` is
   load-bearing**: removing it makes the b-class `dec#1` take the `lt_dec2`
   branch even when `b==0` (traced: the NO_MORE_CARRY check fires after
   `dec(0)`), which loops forever.
5. **NO_MORE_CARRY polarity confirmed on EQ**: armed iff the pre-decrement
   value was >= 1 (no borrow). EQ(2,0) falls through `NO_MORE_CARRY_FLAG
   op2_nonzero` straight to `diff_is_2`.
6. **The memory budget is knife-edged**: the compare section may not exceed
   roughly +10 atoms over EQ's (130); 57,517 bytes with 1,532 headroom is the
   current best, and a single reference-value change can push the init code
   over.
7. **Decisive negative result (measured 3 builds per variant)**: the routing
   fix cannot be a repoint. Repointing the tail's `SUBROUTINE_FLAG6` line to
   the dispatcher (`lt_dec2_ret`) - semantically correct, ZERO atom change -
   breaks EVERY CMP vector including `(0,0)`, which never executes that line:
   all nine print `a8` in an EOF loop, and the LIFO baseline's second OUT
   stops popping Slot 0 (`42` instead of `4241`). Repeating the build three
   times gives the same 0/9, so it is not layout lottery. Cause: LMAO's init
   code is **byte-determinative**: the data-module constant chain that writes
   a cell's initial value has a value-dependent length, and the trampoline
   cells' effective opcodes are position-dependent (`(mem[c]+c) % 94`), so
   changing one referenced address changes the init bytes, the trampoline
   xlat2 cycles shift, and `SLOT1_FLAG` - which decides slot0-vs-slot1 in
   every OUT - flips. Adding the router line inside `lt_false` instead fails
   the build outright (init-code overlap).
8. **`.OFFSET` pinning was tried and fails closed** (measured): pinning
   `SLOT0_FLAG`/`SLOT1_FLAG` at their current addresses (57588/57592) makes the
   build fail with "Memory usage conflict ... a .OFFSET directive may
   conflict" - the pinned program blocks sit where the (now longer) init code
   needs to reach, with or without the repoint. The program region is densely
   packed (HALT 57435, OUT 57459, IN 57477, MOVD 57494, ROT 57497, NOP 57535,
   SLOT0 57588, SLOT1 57592, ...), so there is no free gap to pin into.
9. **It is not a layout shift after all** (measured, v25): the repointed
   variant produces the SAME image size (57,517), the SAME trampoline
   addresses (SLOT0 57588, SLOT1 57592, HALT 57435, OUT 57459) as the
   working 8/12 variant. Only the init-code bytes inside LMAO's constant
   generation differ (one cell's address value), yet the OUT's slot choice
   flips for every vector including `(0,0)`, which never executes the
   repointed line. Dropping the now-dead `OP1_FLAG` line at
   `return_from_dec_op2_1` (-3 atoms, correct once both `dec#2` returns route
   via the SUB6 line) does not help either. The breakage lives inside LMAO's
   init-code generation, not in anything the HeLL source controls.
10. **Both `dec#2`-via-`SUB5` variants hit a second, different bug** (v26,
    v27, traced): routing both `dec#2` returns through
    `return_from_dec_op2_1` (where the existing `OP1_FLAG` line routes them
    correctly - verified in the trace at step ~71,042) makes the b-class
    `dec#1` take the `lt_dec2` branch even when `b == 0`: the
    `NO_MORE_CARRY_FLAG` check fires after `dec(0)`, which it must not (the
    polarity is confirmed on EQ: armed iff the pre-decrement value was >= 1).
    Splitting `lt_dec2` per class costs +6 atoms and does not fit the memory
    budget (build fails). Combined with finding 9, the practical conclusion
    is that **the routing cannot be moved inside this image at all**: any
    reference/value change in the compare section lands in a different LMAO
    init-code basin where either the OUT's slot choice or the
    `NO_MORE_CARRY` semantics flips.
11. **The byte-level mechanism is pinned down**: comparing a working and a
    broken image of the same length shows the differing bytes are all in
    57416-57512 - the tail of LMAO's init code, from which the interpreter's
    crazy-fill derives the initial values of every cell after the file's end,
    including the flag trampolines (`SLOT0_FLAG` 57588, `SLOT1_FLAG` 57592).
    Trampoline opcodes are position-and-value dependent, so a different init
    tail changes the trampolines' xlat2 cycles. 14 semantically-neutral
    dead-block permutations of the correct-routing source all gave 0/9, so
    the basin is stable per compare-section content, not per layout noise.
12. **The lottery-immune fix (measured, ready to implement)**: in a broken
    basin every OUT pops Slot 1 - probed on the 0/9 image, all OUTs print
    `59048` (the EOF/fill value of the cleared Slot 1) regardless of operand,
    i.e. the slot choice is not data-dependent, it is purely the trampoline's
    xlat2 cycle. Therefore the fix that does not depend on the basin at all:
    **leave the compare result in BOTH slots.** The result push ends in
    `add_push0_done`, which is exclusive to the compare path (the OUT-opcode
    pop never passes through it - it goes `return_from_st1_4` ->
    `ret_rst_st1_3` -> `reset_and_loop` directly), and its chain currently
    RESETS Slot 1 to C1 (empty). Replacing that reset with a copy of Slot 0
    (read Slot 0 with the double-`ROT C2 R_ROT` idiom into A, crazy it into
    `stack_top_1`) costs roughly +8-10 atoms and makes the OUT print the
    result whether it pops Slot 0 (working basin) or Slot 1 (broken basin).
    Combined with the routing fix, this lands all 9 pairs.
13. **Viable next moves**: (a) implement 12 (the copy in `add_push0_done`)
    together with the `SUBROUTINE_FLAG6` repoint, accepting the atom cost and
    cutting the ~10 atoms back from the EQ-verbatim push tail (`ROT C1 R_ROT`
    in `diff_is_2` is the first candidate - it only pre-loads A for the
    `stack_scratch` crazy); (b) shrink the compare section by ~10 atoms and
    retry the routing fix alone inside that smaller basin; (c) inspect
    `third_party/lmao/src/gen_init.c` for a deterministic mode; (d) accept
    8/12 and fix the independent push-encoding defect (the true-push prints
    `02` instead of `01`).

## Findings added 2026-10-10 (new experiments, oracle==runner on every vector)

Two further routing variants were built and run against the 12-vector harness.
Both **fit** the memory budget and both reproduce `print == b`-derived value
independent of `a` (7/12), which **falsifies the "basin / slot lottery" framing**
of findings 7-12 as the primary blocker.

14. **The blocker is result propagation, not the OUT slot lottery** (measured):
    - `BASEC` = HEAD + `SUBROUTINE_FLAG6` repoint (H6) + dead-`OP1_FLAG` cut
      (OP1DEAD): builds at **56,947 bytes**, harness **7/12**, oracle==runner.
      Output is `00` for `b in {0,1}` and `02` for `b==2`, independent of `a`.
    - `13(a)` = H6 routing fix **+** the both-slots copy chain (finding 12:
      replace the `add_push0_done` Slot-1 reset with a Slot0->Slot1 copy via
      `V10ROW/V10S1/V10S2/V10S3`). Builds at **57,517 bytes** (fits), harness
      **7/12**, oracle==runner. The step trace (`lt_trace2.py` on `(0,2)`) shows
      pass 2 now **completes**: `lt_a_pop -> lt_a_dec1_ret -> lt_a_dec2_ret ->
      diff_is_2 -> add_rst0_done -> load_diff_1 -> add_push_common ->
      add_push0_done -> return_from_stack_top_3` (steps ~26.9k-30.5k), i.e. the
      compare reaches the boolean and the push automaton. **Yet `OUT` still
      prints the `b`-derived value.** With the result present in BOTH slots
      (the lottery-immune construction) the printed value is still wrong, so
      making `OUT`'s slot choice irrelevant does **not** fix it.

    Conclusion: the defect is upstream of the slot choice — the CMP result is
    never landed into a cell whose value dominates the `OUT`'s printed `A`;
    the printed value is governed by the popped operand `b` (pass-1 leftover),
    not by the pass-2 boolean. The next attempt must target the value/encoding
    of the result push and its interaction with the post-compare `OUT`
    automaton (finding 13d), not the trampoline basin.
    Artifacts (this session): `13(a)` `.mb` sha256
    `a2e8cad66ba955e567cc685cdcd0c137f01ca294aeabccd184c394a0618626d4`
    (57,517 bytes), retained outside the repo for reference. Debug tooling
    added: `vm_malbolge/tests/lt_harness.py` (12-vector differential harness)
    and `vm_malbolge/tools/lt_trace2.py` (label/op/MOVD/JMP control-flow
    tracer over the `.dbg`).

15. **Exact functional defect isolated (traced `13(a)` on `(0,2)`)**: the only
    cell that ever executes opcode `OUT` (op 5) and prints is at step **73653**
    with `A = 2` (= the operand `b`). Every other `JMP-> OUT @ 57476` is the
    crazy-fill sweep passing over the OUT cell while it is not yet in its OUT
    xlat2 phase (no print). Reading the slot cells at that step: `stack_top`
    (Slot 0) = `0` (the operand `a`) and `stack_top_1` (Slot 1) = `2` (the
    operand `b`). The two slots still hold the **original operands** — the
    compare result `1` (correct, `lt_true` does fire at steps 73624/73642) is
    never landed into Slot 0, and Slot 1 is never reset to empty. Because Slot
    1 is non-empty, the `OUT` opcode takes the `return_from_st1_4` pop-Slot-1
    branch and prints `b`.

    Contrast with the frozen, working `CMP_EQ` (`P2_STATUS.md`): after its
    compare the result is in Slot 0 and Slot 1 is cleared, so `OUT` falls to
    pop-Slot-0 and prints the boolean. **The `CMP_LT` fork reaches the correct
    verdict but does not reproduce that push/clear tail** — its push machinery
    runs (`add_push_common`/`add_push0_done`/`ret_rst_st1_3` all execute, and
    `lt_true` fires spuriously *during the push* at 73624/73642, indicating the
    compare branch and the push automaton share routing state that should be
    exclusive). This is a concrete, localizable target, not a lottery.

16. **`gen_init.c` inspected (finding 13c) — no deterministic mode**: the init
    tail length is inherently value-dependent by construction —
    `load_constant_to_a_reg(..., constant, ..., rotations, crazy_C2_first, ...)`
    emits a different instruction sequence per constant/address, and
    `set_dreg` walks D to each target. There is no flag to make the codegen
    basin-invariant; only patching vendored LMAO (out of scope, breaks
    `third_party/PROVENANCE.md`) could change that. So finding 13c is a dead
    end and finding 15 (fix the push/clear tail to match `CMP_EQ`) is the live
    path. It must be re-verified for both the 12-vector result AND the memory
    budget after every edit, because the same edits that fix the tail can
    re-roll the basin (findings 7-11).

## Findings added 2026-10-11 (deterministic-defect evidence, oracle==runner on every vector)

HEAD re-verified after restoring the tree from probe builds: harness **8/12**,
`mbir_cmp_lt.mb` sha256 `4a38722a…` (table below), failures `(0,1)->00` @79,167,
`(0,2)->02`, `(1,2)->02`, `(2,2)->02` @78,974 — identical on both engines.

17. **The present defect is deterministic, not a basin** (measured): LMAO seeds
    `srand(time(NULL))` (`third_party/lmao/src/main.c:222`) and fills padding
    with `nop_opcodes[rand()%8]` (`initialize.c:414-419`) — same source,
    different image *bytes* per build, same length and same behavior. Three
    consecutive rebuilds of `BASEC` and of `13(a)` scored the same 7/12 with
    per-vector step counts identical, so the failures of findings 14-16 are
    semantic, not layout lottery. This formally retires the "init-basin
    lottery" framing of findings 7-13 for the current blocker.

18. **Measured invariant at `OUT`** across HEAD / BASE / BASEC / 13(a): the
    printed value is operand-derived (exactly `b` in the BASE variants), and
    the two slots still hold the original operands `(a, b)`; `stack_top`
    receives no write after the operand push (BASE `(0,2)`: last
    `CRAZY->stack_top` @60,228 writes the pushed `a=0`; nothing until `HALT`
    @76,606). Slot 1 only ever sees read-idiom write-backs (1→2 pairs).

19. **`R_MOVED` restoration experiments** (BASE variants): restoring EQ's
    preserved `R_MOVED` in `diff_is_2` only (MV2) is **neutral** (7/12, same
    failing vectors); additionally restoring it in `dispatch_02` (MV12) is
    **catastrophic** (3/12: `b=0` vectors print `a8` in an EOF loop, `b>=1`
    vectors do not terminate by 600,000 steps). LT's deliberate drops of
    those `R_MOVED` lines were required by LT's different MOVED-flag state
    at dispatch.

20. **MOVd-target-level trace localizes the break** (BASE build, `(0,2)`,
    `lt_trace2.py`): pass-1 pop completes (`add_pop1_done` @69,020); the
    classify chain is genuinely entered (`return_from_dec_op2_1` @69,577;
    `lt_dec2`/`lt_dec2_ret` armed @70,113/70,118); control then lands on the
    `lt_false` head cell **six times** (70,151-70,279) — yet the
    boolean-encoder blocks never execute (no `MOVD`-arm into
    `diff_is_2`/`lt_true` targets, no `stack_scratch` crazy in that window).
    What follows instead is a ~2,900-step generic subroutine unwind
    (`return_from_decrement_value_1..3` → `disc_1`/`disc_2`, value-division
    loops 3159→1053→351→117→39→13), and the trailing generic dispatch
    performs a second Slot-1 read (`return_from_stack_top_2/3` chain,
    `return_from_st1_3` armed @73,071) so `OUT` @73,078 prints `b`.
    **Conclusion:** the verdict automaton reaches the true/false routing but
    its exit trampoline never hands control to `diff_is_2` → result push;
    the fix target is the dec-exit → classification-completion landing —
    consistent with finding 15's push/clear-tail target, and now demonstrably
    upstream of both the OUT slot choice (finding 14) and any basin concern
    (finding 17).

**Trace-methodology caveat:** the `.dbg LABELS`-range attribution in
`lt_trace2.py` misnames cells of the NOP padding sweep adjacent to a label
(e.g. the `~lt_false`/`~add_push0_done` floods in `lt_slotprobe.py` bisect
output). The trustworthy signals are `MOVd` target cells, jumps landing
exactly on label head cells, and slot/cell value-write events.
